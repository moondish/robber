### 已选状态来源

`PartDisplay` 课程列表本身不包含已选状态。页面中的绿色“已选”是前端合并以下数据后显示的：

- `PartDisplay.tmpList`：课程和教学班
- `ChoosedDisplay`：已选课程，带 `sfxkbj=1`、`isInxksj=1`

当前代码每次查询后建立一次已选索引，按 `kch/kch_id/jxb_id` 标记课程。命中的目标如果已在已选列表，会直接判定完成，不再重复提交；候选列表也会过滤已选课程。

## 4. 提交返回语义

HAR 中的真实提交返回：

### 冲突

```json
{"flag":"0","msg":"所选教学班的上课时间与其他教学班有冲突！"}
```

### 容量不足

```json
{"flag":"-1","msg":"0,<jxb_id>,110,"}
```

前端 JS 对 `flag=-1` 的处理是更新容量信息，不视为成功。当前代码同样按失败处理并继续轮询。

成功条件仍为：

```text
flag=1
success=true
响应值 1
消息明确包含“成功”
```

## 6. 抢课流程测试

当前实现链路：

```text
PartDisplay
  -> 目标匹配
  -> 已选检测
  -> detail 获取 do_jxb_id
  -> 可选 title 探针
  -> submit
  -> 成功退出或继续轮询
```

当前真实测试停在第 3 步：

```text
detail -> "0"
```

因此本轮无法取得新的 `do_jxb_id`，不能继续实际提交。代码会按配置间隔继续重试，并在连续 5 次目标流程失败后展示候选选择。

## 7. 自动重试与候选选择

- 查询无命中：不设固定 60 秒冷却，按 `intervalSec` 轮询。
- 连续 5 次无命中：按人数和剩余容量展示候选。
- 选课流程连续失败 5 次：包括详情返回 `0`、没有 `do_jxb_id`、探针失败、提交失败、流程异常。
- 候选排除刚刚失败的教学班。
- 交互终端输入编号可快速尝试新候选。
- 成功或确认已选后失败计数清零。

## 9. 风险与未确认项

1. 没有成功提交的 HAR，无法证明服务端成功返回后所有状态正确。
2. 没有退选请求，自动退选参数只能视为“结构合理”，不能视为已验证。
3. `title` 和 `batch` 在本校当前 HAR 中没有出现。
4. `do_jxb_id` 具有强时效性，必须在命中课程后实时获取。
5. 当前目标教学班无可选容量，实际抢课必须等待服务端返回教学班详情。

## 10. 最终判断

- 查询、已选、提示、轮次和提交字段构造：**可信**
- 当前无课可选的详情返回：**接口正常，业务未开放**
- 成功提交、退选和冲突自动处理：**尚缺真实成功样本，不能保证**
